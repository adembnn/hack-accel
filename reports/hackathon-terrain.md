## Aiven Runtime en pratique (octobre 2026)

- **C'est quoi** : environnement managé pour exécuter apps et agents conteneurisés **dans le même projet que les bases Aiven**. Ex-"Aiven Apps" (annoncé 8 avr. 2026), **disponible en général depuis le 23 sept. 2026**, sur AWS et Google Cloud (Azure à venir). [Blog GA](https://aiven.io/blog/deploy-your-apps-and-agents-where-your-data-lives-with-aiven-runtime) · [Communiqué](https://aiven.io/press/aiven-launches-runtime-and-datahub-enabling-ai-agents)
- **Déployer (étapes docs)** : Console > projet > Runtime > Deploy application > connecter GitHub > repo + branche > choisir le manifeste > Scan > Deploy. **Un push GitHub ne redéploie pas** : il faut "Deploy latest commit" à la main. [Docs deploy](https://aiven.io/docs/products/runtime/deploy-apps)
- **Manifestes** : Containerfile/Dockerfile (ports lus depuis `EXPOSE`, env depuis `ENV`) et/ou Docker Compose multi-services. Tout ce qui se conteneurise tourne. [Docs manifestes](https://aiven.io/docs/products/runtime/manifest-files/manifests) · [Containerfiles](https://aiven.io/docs/products/runtime/manifest-files/containerfiles) · [FAQ](https://aiven.io/runtime)
- **Magie Compose** : les images `postgres`, `valkey`/`redis`, `opensearchproject/opensearch`, `apache/kafka` sont reconnues et remplacées par de vrais services Aiven (version = dernière stable). **ClickHouse n'apparaît pas dans la liste de détection** : il faudra probablement le créer à part et passer l'URL à la main (déduction, non vérifié). [Docs Compose](https://aiven.io/docs/products/runtime/manifest-files/compose-files)
- **Variables injectées** : `DATABASE_URL`, `VALKEY_URL`, `OPENSEARCH_URI`, et pour Kafka `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_SECURITY_PROTOCOL` (SSL), `KAFKA_ACCESS_KEY`, `KAFKA_ACCESS_CERT`, `KAFKA_CA_CERT`. Pas de variables host/port/user séparées : adapter le code à une URI (ex. pas de `PGHOST`). Secrets via la Console. [Docs variables](https://aiven.io/docs/products/runtime/secrets-and-variables)
- **Réseau** : exposition publique HTTP/S en ajoutant un port (domaine affiché dans "Connection information") ; ports sortants bloqués : 23, 25, 119, 135, 137, 138, 139, 179, 445, 465, 631. Cette page s'intitule encore "Aiven Apps / Limited availability" (juillet 2026) : à vérifier sur place. Les apps peuvent appeler des services non-Aiven. [Docs ports](https://aiven.io/docs/products/apps/ports) · [FAQ](https://aiven.io/runtime)
- **Prix/limites** : à partir de 7 $/mois (0,01 $/h), 9 plans, 0,5 CPU et 0,25-8 Go de RAM sur la fourchette affichée ; facturation à l'heure tant que l'app tourne, passage prévu à l'usage. Les crédits hackathon couvrent ça. Pas de page "limitations" (404). [Pricing Runtime](https://aiven.io/pricing/runtime)
- **Gratuit** : plans free pour PostgreSQL, MySQL, OpenSearch, Kafka, Valkey (pas ClickHouse) ; Postgres free = 1 CPU / 1 Go RAM / 1 Go. [Pricing](https://aiven.io/pricing)
- **Pilotage par agent** : Aiven MCP (hébergé `mcp.aiven.live`, OAuth) permet à Claude Code/Cursor de créer un service Postgres, lancer du SQL, créer des topics Kafka et **déployer sur Runtime** ; un admin d'organisation doit activer "Allow MCP connection" ; il redacte les identifiants par défaut. Couvre PostgreSQL et Kafka seulement. Commande : `claude mcp add --transport http aiven-mcp https://mcp.aiven.live/mcp`. [Blog MCP](https://aiven.io/blog/aiven-mcp) · [Blog Lovable](https://aiven.io/blog/lovable-database-aiven-postgresql) · [Page MCP](https://aiven.io/mcp)
- **DataHub** (GA aussi le 23 sept.) : catalogue/lignée/gouvernance servi aux agents via MCP. [Blog GA](https://aiven.io/blog/deploy-your-apps-and-agents-where-your-data-lives-with-aiven-runtime)

**Ce que le discours Aiven met en avant (donc ce qu'un juge Aiven aime entendre)** :

[Blog GA](https://aiven.io/blog/deploy-your-apps-and-agents-where-your-data-lives-with-aiven-runtime)

- Open source, pas de lock-in, "fresh, fast, governed, reachable". [Blog Builders](https://aiven.io/blog/let-builders-build-and-agents-cook)

## Ce qui est typique vs ce qui manque

Base de preuves faible : 0 résultat de la série, 2 événements Accel/Aiven voisins, 1 événement Paris non Accel. Ce qui suit est mon analyse, pas un fait sourcé.

**Typique (à éviter ou à surclasser)**
- Agents "personnels" : mémoire locale, podcasts perso, santé/mouvement, suivi de temps ; assistants verticaux génériques (Stanford ALP, AI Tinkerers ci-dessus).
- Outils de dev autour de MCP.
- Pour ce brief précis : "chat avec tes données" sur Postgres, RAG sur OpenSearch, dashboard Kafka. Ce sont les usages que la doc Aiven suggère elle-même, donc que la plupart des équipes prendront.
- Un modèle qui "wrappe" un LLM sans donnée propre à l'utilisateur.

**Ce qui manque / angles sous-représentés**
- Un client nommé avec une donnée qui n'existe que chez lui (jury Amsterdam : "named customer", "company potential").
- Une preuve chiffrée, pas un score de jury : avantage mesurable (Amsterdam l'exige explicitement).
- Une vraie dépendance aux données dans la durée : l'agent s'améliore avec les exécutions passées, mémoire longue, flux d'événements, plutôt qu'une requête ponctuelle. C'est la liste du brief, et les gagnants connus l'exploitent peu (hypothèse).
- Usage honnête de plusieurs services Aiven pour des raisons techniques justifiées (flux Kafka -> analytique ClickHouse -> cache sémantique Valkey), pas par cochage.
- Parcours vers les premiers utilisateurs (brief) : aucun gagnant connu ne montre un canal de distribution concret.
- Gouvernance/PII (Aiven la met en avant) : rarement traité en hackathon.
